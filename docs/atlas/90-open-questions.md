| OPEN-13 | For now, nothing is pre-seeded: the first `docker compose up` prewarms from live data (fetch eight weeks from Arctic Shift, embed, place, tag day by day) and the reviewer waits it out (Brian, 2026-10-18). Still open, to revisit once prewarm is built and timed: (1) how long it takes, likely minutes, dominated by a few hundred tagging calls and embedding on the laptop's processor; (2) the demo then depends on Arctic Shift being up and on the OpenRouter key working at the moment the reviewer starts it, and the tagging calls during prewarm are paid from that key; (3) If prewarm proves slow or fragile, the fallback is committing the computed database. | [04](04-environment.md) |
| OPEN-21 | The grounded-claims measurement judges the two versions by different rules, which makes the centerpiece unfair. Plate 70 counts a version B claim as grounded if the post it cites exists, but checks version A's claims by meaning against the week's posts. Version B could cite a real post that doesn't support the claim and still score. The recommendation: judge every claim from both versions the same way, by meaning, against the posts in the range; for version B, additionally report how many of its citations actually support the sentence they're attached to. | [70](70-comparison.md) |
| OPEN-22 | What is the prediction score for a report on an arbitrary date range? The backtest on plate 50 is a fixed experiment (hold back the latest week), but reports can now be generated for any range, and the Comparison screen shows a prediction score per run. The recommendation: every comparison run also writes both versions' predictions for the range just before the requested one, and scores them against the requested range, which has already happened. That gives every run its own prediction score using only data from before the range. The first range in the history has nothing before it and shows no score. | [50](50-prediction.md), [70](70-comparison.md) |
| OPEN-23 | The dot-plot layout can't be learned from the full history on first start, because first start processes the history one day at a time and the full history doesn't exist until the last day is done. The recommendation: the first catch-up runs in two passes, first fetching and embedding all fifty-six days and learning the layout from them, then placing, clustering and tagging day by day in order. Later catch-ups place new posts into that layout. Clustering is unaffected because it doesn't use the 2D positions. | [40](40-backend.md), [21](20-data-model/21-topics.md) |
| OPEN-24 | A run is recorded in three places: LangGraph's own saved checkpoints (plate 60), the live-event log (plate 41), and the comparison_runs table (plate 70). Three records of the same run can disagree, and nothing says which one the Runs screen and the replay read. The recommendation: drop LangGraph's checkpoints, which exist to resume a half-finished agent and which we don't need; keep the event log as the step-by-step record, and comparison_runs as the summary with the final documents and scores. | [41](40-backend/41-live-events.md), [60](60-agents.md), [70](70-comparison.md) |
| OPEN-25 | What form is the document in? Plate 30 says it's rendered from markdown; plate 70 needs it as a list of claims, each with the posts it cites, so claims can be checked and highlighted. The recommendation: the report agent returns structured output (sections, each made of claims with their cited post ids, plus quotes and predictions), the page renders that, and the markdown export is generated from it. | [30](30-frontend.md), [70](70-comparison.md) |
| OPEN-26 | The brief asks for a document on the past week and the week to come, while the Explore page can generate a report for any date range. Is a report always a week, or any range? The recommendation: allow any range, defaulting the slider to the last seven days so the out-of-the-box report is exactly the brief's weekly document; the prediction covers a period the same length as the range. | [31](30-frontend/31-screens.md), [50](50-prediction.md) |
